# 自我进化 · 操作手册

> 「像 AI 一样自我进化」的落地说明：反馈 → 候选 → 样本外闸门 → 待批准 → 落地/回滚。
> 面向运维与人工裁决者，重点在**安全边界**与**每步能查到什么、能回滚什么**。

---

## 一、统一架构

四层进化能力**不是四个独立功能**，而是共用同一条回路。否则「反馈收集」「样本外验证」
「批准队列」「回滚」会被各写四遍，且各错四遍。

```
                     ┌──────────────────────────────────────────┐
                     │  ① 反馈收集  src/evolution/feedback.py    │
                     │     只读：预测验证 + 交易回流 + 绩效指标    │
                     └──────────────────┬───────────────────────┘
                                        │ PerformanceSnapshot（事实底稿）
        ┌──────────────┬────────────────┼────────────────┬──────────────┐
        ▼              ▼                ▼                ▼              │
  ┌───────────┐ ┌───────────┐  ┌───────────┐  ┌───────────┐            │
  │②A 参数寻优 │ │②B LLM 复盘 │  │②C 模型重训 │  │②D 基因进化 │            │
  │param_search│ │llm_review │  │ retrain   │  │ genetic   │            │
  └─────┬─────┘ └─────┬─────┘  └─────┬─────┘  └─────┬─────┘            │
        │  纯函数·只提候选·不写盘·不自盖章            │                  │
        └──────────────┴────────────────┴────────────────┘              │
                                        ▼                                │
                     ┌──────────────────────────────────────────┐       │
                     │  ③ 样本外闸门  src/evolution/gate.py      │       │
                     │     风控硬线一票否决 → 可评估性 → 指标对比  │       │
                     └──────────────────┬───────────────────────┘       │
                                        ▼                                │
                     ┌──────────────────────────────────────────┐       │
                     │  ④ 待批准队列  src/evolution/store.py     │       │
                     │     pending/approved/rejected/applied/…   │       │
                     └──────────────────┬───────────────────────┘       │
                                        ▼                                │
                     ┌──────────────────────────────────────────┐       │
                     │  ⑤ 唯一写盘口  src/evolution/overrides.py │       │
                     │     落地 + 一键回滚（靠 Change.old）        │       │
                     └──────────────────┬───────────────────────┘       │
                                        └──────── 下个回合读新参数 ──────┘
```

编排在 `src/evolution/runner.py`，CLI 在 `scripts/evolve.py`。

## 二、四个生成器

| 生成器 | 驱动信号 | 提出什么 | 判定方式 |
|---|---|---|---|
| **A** `param_search` | 组合绩效症状（换手/现金拖累/回撤/持仓不满/碎单） | 单个 `trading_loop.*` 参数 | 闸门 A/B 回测 |
| **B** `llm_review` | 同一份事实底稿，让 LLM 做**跨信号**权衡 | 从**封闭动作目录**里选动作 | 闸门 A/B 回测 |
| **C** `retrain` | 预测准确率漂移 | 把 `ml.active_version` 钉到更优的重训产物 | **自带 walk-forward 证据**校验 |
| **D** `genetic` | 参数适应度 | 组合参数的邻域精调（多基因） | 闸门 A/B 回测 |

### 生成器契约（`generators/base.py`）

所有生成器**只做三件事**：读快照、提候选、给理由。它们

* **不写盘** —— 不碰 `config/`、不碰 `data/`；
* **不做决策** —— 不许自己给自己盖 `passed=True`；
* **不落地** —— 落地只能走 `overrides.apply_changes`，且必须人工批准。

这条契约让每个生成器都能离线单测（注入假数据 → 断言产出），也让「谁改了什么」
永远只有一个出口。

### 各自的额外安全设计

**B（LLM 复盘）** —— LLM 是「会一本正经胡说八道的外部依赖」，所以：

* LLM **不产出任何数值**。它只能从 `llm_review.ACTIONS` 这份封闭目录里挑一个动作 id；
  真正写进候选的数值由代码按 `ParamSpec.step` 算出。于是「让 LLM 把熔断线调到 50%」
  **在结构上不可能** —— 它没有地方说这个数。
* 目录本身也受校验（`catalog_problems()`）：每个动作指向的参数必须在白名单内、
  不得是风控硬线；目录坏了就**停手**，不按一份可能越界的目录去改参数。
* LLM 的 `confidence` 只写进 `meta` 供人审阅，**不参与任何自动决策**。
* LLM 挂了 / 余额不足 / 回复是乱码 → 返回空列表并告警，**不抛异常**。

**C（模型重训）** —— 换模型会改变评分面板本身，没法用同一块面板做 A/B，所以：

* 生成器**绝不训练模型**。训练是运维显式动作（`--retrain`），因为它要写 `models/`、
  耗时数十分钟。
* 生成器只读注册表，比较「现任（钉子）」与「全局样本外最优产物」，产出**自带证据**的候选。
* 证据必须过 `gate.verify_supplied_evaluation`：必须 `passed=True`、`evaluator`
  在白名单内、`reasons`/`delta`/`window` 齐全。生成器自称 `gate:backtest` 会被拒。
* **必须先有基准钉子**（`--pin`）。没有钉子时注册表会自动采用样本外最优产物 ——
  也就是说只要往 `models/` 丢一个新产物的指标文件，它就**已经生效了**，
  绕过闸门与人工批准。这种情形下「更优」没有意义，真正的问题是**静默自动上线**。
  所以第一次建立基准由人拍板；钉住之后，本生成器才在「有基准可比」的前提下做晋升。

**D（基因进化）** —— 三条约束都是为了「别乱搜」：

* 基因组只用**闸门能回测表达**的参数（`GENES = PARAM_SPACE ∩ gate.BACKTEST_MAP`）。
  否则辛苦搜出来的组合含 `scan_interval_sec` 这种不可回测参数，闸门会按
  「整批不可评估」直接驳回，白搜。
* 种群**从当前参数出发**做邻域搜索（第 0 号个体就是当前生效参数），
  每个基因与起点最多相差约 `generations` 个步长 —— 产出可解释，
  不是全空间随机抽到的一个点。
* 适应度与闸门**共用同一条验收边界**：回撤比基准恶化超过 `max_drawdown_worsen`
  直接判 `-inf`。搜出来的冠军天然落在闸门的可接受域内。
* 变异算子是「每次挪定 1 个基因（偶尔 2 个）」，不是「每基因按概率挪」——
  后者在 6 个基因上每次挪 3 个，是随机漂移，**爬不了坡**（实测踩过）。
* 默认随机种子由面板区间派生 → 同一块面板、同一份当前参数，重跑得到同一个答案。
  否则每个回合都会提出一个不同的基因组，把待批队列刷成噪声。

## 三、安全模型（三道锁）

### 锁 1：风控硬线永久不可进化

`space.PROTECTED_NAMESPACES`（`guard.` / `trading_guard.` / `risk.` / `safety.` / `executor.`）
与 `PROTECTED_LEAVES`（熔断线、单票上限、下单频率、止盈止损、`position_sizing_method` 等）
以及裸名歧义项（`max_positions` 必须写全 `trading_loop.max_positions`）。

触碰硬线的候选在**三个环节各拦一次**：生成时 `space.validate`、
闸门 `risk_precheck`（连回测都不跑）、落地前 `runner.apply` 再检一次
（防止有人手改 `candidates.json` 塞进风控参数）。

### 锁 2：方向语义 —— 「更激进」必须人工批准

每个参数登记了 `risk` 方向：

* `neutral` —— 双向都不可怕（调仓容忍带、扫描间隔、权重方式）
* `risky_up` —— 值**调高**更激进（单票权重上限、目标持仓数）
* `risky_down` —— 值**调低**更激进（现金保留比例、选股阈值）

`check_changes_adoptable()` 判定能否自动落地：**必须全部参数都是非激进方向，
且全部标记 `auto_adopt=True`**。否则即便开了 `--auto-apply` 也只进 `pending`。

`ml.active_version`（换模型）**永远 `auto_adopt=False`** —— 它改变所有后续选股，
影响面最大。

### 锁 3：默认不自动落地

`--run` 默认 `auto_apply=False`。`--auto-apply` 只对「安全方向且标记可自动采纳」
的改动生效，且会以 `auto_applied` 状态留痕（与人工落地的 `applied` 区分开）。

## 四、CLI 速查

```bash
# ---------- 看现状（只读，默认动作）----------
py -3.12 scripts/evolve.py --status
py -3.12 scripts/evolve.py --json | jq .           # 供脚本消费
py -3.12 scripts/evolve.py --space                 # 打印可进化参数空间

# ---------- 首次准备 ----------
py -3.12 scripts/evolve.py --doctor                  # ★ 先跑这个：逐条体检 + 给出该跑什么命令
py -3.12 scripts/evolve.py --build-panel --max-stocks 200 --pool hs300   # 建样本外面板（重）
py -3.12 scripts/evolve.py --models                  # 列模型注册表
py -3.12 scripts/evolve.py --pin production_metrics # 建立模型基准（重训晋升的前提）

# ---------- 模型版本的人工批准 ----------
py -3.12 scripts/evolve.py --models                          # 看有哪些键、谁是「可作主模型」的
py -3.12 scripts/evolve.py --approve-model production_metrics --operator alice
py -3.12 scripts/evolve.py --revoke-model production_metrics

# ---------- 跑回合 ----------
py -3.12 scripts/evolve.py --run                                    # 全部生成器
py -3.12 scripts/evolve.py --run --generators param_search,genetic   # 只跑指定生成器
py -3.12 scripts/evolve.py --run --verify                           # 回合前先补验到期预测（会写 prediction_history.json）
py -3.12 scripts/evolve.py --run --auto-apply                       # 允许安全方向自动落地
py -3.12 scripts/evolve.py --run --generators genetic \
    --ga-population 16 --ga-generations 6 --ga-elite 2 --ga-seed 42  # 调 GA 搜索预算

# ---------- 人工裁决 ----------
py -3.12 scripts/evolve.py --show <ID>
py -3.12 scripts/evolve.py --approve <ID> --operator alice
py -3.12 scripts/evolve.py --apply <ID>              # 落地（改运行期参数）
py -3.12 scripts/evolve.py --reject <ID> --reason "样本外不显著"
py -3.12 scripts/evolve.py --rollback <ID>           # 一键回滚

# ---------- 模型重训 ----------
py -3.12 scripts/evolve.py --retrain                 # 离线重训（数十分钟）
py -3.12 scripts/evolve.py --retrain --run --generators retrain  # 重训后立刻生成晋升候选
py -3.12 scripts/evolve.py --unpin                   # 取消基准钉子（回到自动挑选）

# ---------- 维护 ----------
py -3.12 scripts/evolve.py --reset-overrides         # 清空全部参数覆盖，恢复默认
```

退出码：`0` 正常；`1` 参数/执行错误；`2` 前置条件不满足。

### 闭环链路（把 ①选股 → ④业绩 真的跑起来）

```bash
# ① 选股：产出 data/daily_reports/daily_picks_*.json
py -3.12 scripts/daily_pick.py                        # 按配置（zz500 / 20 只）
py -3.12 scripts/daily_pick.py --pool hs300 --top 30 --min-score 52
py -3.12 scripts/daily_pick.py --build-plan           # 选完立刻刷新交易计划
py -3.12 scripts/daily_pick.py --json                 # 机器可读
#   退出码：0 有标的 / 3 选股成功但无标的（空仓合法） / 2 生成出错

# ② 只预演「本该下什么单」（不产生任何交易，风控状态隔离到 loop_rehearsal/）
py -3.12 scripts/run_loop.py --preview

# ③ 真跑闭环（默认纸交易 / 模拟盘，无需 QMT）
py -3.12 scripts/run_loop.py --once                   # 只跑一个周期
py -3.12 scripts/run_loop.py --until-close            # 常驻，收盘结算完自动退出
py -3.12 scripts/run_loop.py --dry-run                # 连纸单都不下
py -3.12 scripts/run_loop.py --rebaseline-peak --resume   # 换账号/出入金后重置净值基线

# ④ 看业绩
ls data/loop_reports/                                 # loop_report_YYYYMMDD.{json,md}
py -3.12 scripts/evolve.py --doctor                   # 第 4 项会告诉你有没有结算过
```

⚠️ **别用 `scripts/daily_recommend.py`** —— 那是另一条路径，只写 CSV 到 `logs/`，
**不产出** `daily_picks_*.json`，喂不饱闭环。闭环要的是 `scripts/daily_pick.py`。

⚠️ **常驻闭环要跨日**：计划是收盘后为**下一个交易日**生成的，闭环会在跨日时
回磁盘重读当天计划（见第十一节）。所以别每天手动重启，让它跑着即可。

## 六、运维流程

### 首次上手（五步）

0. `--doctor` **先体检**。它会逐条告诉你缺什么、该跑什么命令。
   阻塞项（没有面板 / 闭环从未结算）不解决，进化回合会「安静地什么都不做」。
1. `--build-panel` 建样本外面板。**没有面板闸门无法判定，所有候选会被拒。**
2. `--models` 看注册表，挑一个「✅可作主模型」的键 `--pin` 定基准。
   注意 `🧩集成腿` 那一类**不能**作主模型，钉它会被拒绝。
3. `--approve-model <键>` 把该版本加入人工批准名单。
   （不批准也能跑，只是「批准与否」目前还不影响加载 —— 见第八节。）
4. `--run` 跑一个回合，看 `--status` 里出现了什么候选。
5. 逐条 `--show` 审阅理由与证据，满意就 `--approve` → `--apply`。

### 日常

* 回合可以挂在调度里（例如收盘后），但**默认不自动落地**，
  所以最坏情况只是待批队列多几条，不会改变系统行为。
* 想让它更自动，就先观察一段时间 `--run --auto-apply` 都在自动落地什么，
  确认方向无问题后再长期启用。**永远可以先 `--rollback`。**

### 模型重训闭环

`--retrain` 只训练、不上线；上线四步走：

```
--retrain  →  --models（找到新产物键）  →  --run --generators retrain（生成晋升候选）
           →  --approve <ID>  →  --apply <ID>
```

## 七、测试与零污染纪律

### 铁律

* 所有测试必须 `tmp_path` / `monkeypatch` 隔离；任何一处写真实状态文件都是事故。
* 跑完全量测试后**必须核对**生产文件的 md5 未变：

```bash
for f in data/trading_guard_state.json data/trading_journal.jsonl \
         data/evolution_state.json config/evolution_overrides.json \
         data/prediction_history.json; do md5sum "$f"; done
```

* `data/prediction_history.json` 的 mtime 变化**不一定是测试污染** ——
  运行中的看板/调度进程（APScheduler → `tracker_v2.verify_all_pending`）会自己写它。
  判定方法：查 `Get-CimInstance Win32_Process`，看有没有从早就在跑的 `python -m streamlit`
  进程；以及做「无测试运行」的对照组观察。

* **比 md5 更可靠的判据是「文件内有没有多出跑测当天的时间戳」**。
  看板/调度合法写入会让 md5 变化，所以 md5 变了不代表出事；
  但若某个状态文件里出现了**恰好等于跑测时刻**的 `verified_at` /
  `settled_at`，那就是测试污染，没有第二种解释。

### 「作业函数」必须顺着调用链查一遍写盘口

这是本项目**已经踩过两次**的坑，共同点是：被调用的那个函数自己会写盘，
而调用方以为「我只传了 `dry_run=True`」或者「我只改了日历」。

| 案例 | 表面看 | 实际上 |
|---|---|---|
| `test_scheduler.py` → `auto_scheduler.job_evolution()` | 测试调了作业函数 | 它内部 `tracker.verify_all_pending()` **直写真实** `data/prediction_history.json`；`job_evolution()` 根本不接受 `dry_run` |
| `test_loop.py` → `TradingLoop.tick()` | 夹具改了 `calendar` | 墙钟 16:41 已过 `settle_hour=15` → `_should_settle` 为真 → `_settle()` → `Path(DATA_DIR)/"loop_reports"` **写出两份伪造结算报告** |

所以纪律是：

1. **凡是「作业函数」，都要顺着内部调用链查一遍有没有直写生产文件的分支。**
   `dry_run=True` 不等于零污染 —— 它只约束被显式检查的地方。
2. **隔离要覆盖「所有会被这一路径碰到的目录」，而不是「我以为它会写的那个」。**
   `test_loop.py` 的 autouse 夹具原先只隔离 `guard.DATA_DIR`，漏了 `loop.DATA_DIR`；
   现在两者都掐掉，并且**用行为验证**：真的跑一遍结算 tick，
   然后核对真实 `data/loop_reports` 逐字节没变。
3. **顺手做一次负向对照**。隔离断言如果是永真的（比如结算分支压根没跑），
   它会永远绿着骗人。验证办法：临时把隔离去掉跑一次，确认**真的**会写出文件 ——

## 八、加载路径：一个比「静默上线」更要紧的事实

先说结论：**注册表的排序、`ml.active_version` 的钉子、人工批准名单，
目前都不改变系统实际加载哪个模型文件。**

实际加载路径是硬编码的：

```
predictor._load_models()
  → trainer.load_model("xgboost")      # → models/xgboost_model.pkl
  → trainer.load_preprocessing()       # → models/scaler.pkl + label_encoder.pkl
  → _load_feature_list("xgboost")      # → models/features_xgboost.json
```

`model_registry` 里没有任何一行代码影响这三步。所以：

* 注册表说「可作主模型的最优：production_metrics」，只是**描述**了
  `xgboost_model.pkl` 自己那份指标；它并不去换文件。
* 钉住 `ml.active_version`，只改变日志与看板展示，不改变加载。
* 换句话说，**「静默自动上线」这条通道其实并不存在** ——
  它不存在的原因不是被防住了，而是**上线这条路根本还没接通**。
  原先文档把风险写反了：真正的风险不是「悄悄上线」，而是
  「以为上线了，其实什么都没变」。

这件事的严重性在于它会让**生成器 C 成为一个空转的部件**：
它辛苦比对「现任 vs 挑战者」并产出晋升候选，批准落地后 `ml.active_version`
被改写，然后……没有任何东西去读它。

要接通，需要两件事，缺一不可：

1. **产物按版本命名**。现在重训是**覆盖同名文件**的
   （`xgb_model.pkl` / `scaler.pkl` / `features_xgboost.json` 原地覆盖），
   根本不存在「另一个可切换的产物」。必须先有
   `v20261014_xgboost_model.pkl` + `v20261014_scaler.pkl` +
   `features_v20261014.json` 这样成组出现的版本集。
2. **加载器读裁决**。`_load_models` 改为向
   `model_registry.resolve_active_path()` 要路径，并且拒绝加载
   「三件套不齐」的版本集（否则会拿 A 版的 scaler 去跑 B 版的模型）。

当前代码已经到位的是**裁决层**：`resolve_active()` 会给出「该用哪个」，
且没有人工批准时一律返回 `None`（回退生产默认）——
行为与今天完全一致，但语义从「碰巧」变成了「明确」。
`predictor._log_model_resolution()` 每次加载都会把
「裁决 vs 实际加载」并排打进日志，两者不一致时明确告警。

## 十、LLM 通道：云端与本地

LLM 用于两处：**看板「AI 个股分析」** 与 **生成器 B（自我复盘）**。
两者同源，都走 `src/models/llm.py`，因此切换一次即可同时生效。

### 三种 provider

| `provider` | 指向 | 需要 Key | 费用 |
|---|---|---|---|
| `auto` / `deepseek`（默认） | `https://api.deepseek.com` | ✅ 真 Key + 余额 | 按量计费 |
| `local` | 本机任意 OpenAI 兼容服务 | ❌ 不需要 | **0** |

`local` 支持三种常见运行时（都是 OpenAI 兼容接口，只差端口）：

| 运行时 | 默认地址 | 备注 |
|---|---|---|
| Ollama | `http://localhost:11434/v1` | 需 `ollama serve` + `ollama pull <模型>` |
| LM Studio | `http://localhost:1234/v1` | 需先在界面里 **Start Server** |
| vLLM | `http://localhost:8000/v1` | 需先起 OpenAI API server |

### 怎么切

* **看板**：「⚙️ 设置 → AI 大模型配置」→ 选「🖥️ 本地服务」→ 填地址 →
  **「🔍 探测」** 拉取本机模型名做下拉 → 保存。
* **手改配置**：编辑 `config/deepseek.yaml`
  ```yaml
  provider: local
  base_url: http://localhost:11434/v1
  model: qwen2.5:7b
  api_key: ""        # 留空即可，模块会自动补占位 key
  ```

`base_url` 三种写法都收：`.../v1`、`.../v1/`、`.../v1/chat/completions`。

### 显存怎么选（本机实测 RTX 4050 Laptop / 6 GB）

* 7B **Q4 量化**（约 4–5 GB）→ 可行，推荐；
* 3B → 更稳，留给特征工程与回测并行跑的场景；
* 7B **未量化**（约 14 GB）→ 直接爆显存，别试。

### ⚠️ 回环地址必须绕过代理（本机就踩了）

环境里常有 `HTTP_PROXY`（本机此刻是 `http://127.0.0.1:57236`），
而 `NO_PROXY` 往往没配。于是连 `http://localhost:11434` 这种回环请求
也会被 requests 交给代理，代理不认识它，回一个 **502 Bad Gateway**。

表现出来就是「Ollama 明明 `ollama serve` 起来了，就是连不上」——
而 502 完全不会指向代理，靠自己几乎不可能想到。
模块已对回环地址自动绕过代理；**云端地址不受影响**（可能确实需要代理出网）。

### 第三批：把「连本地」这条路真正接通（2026-10-14 晚）

起因是用户一句「DeepSeek 连接本地不行吗？」。答案分两层：
**代码里确实有 bug 挡着（已修），但本机也确实没跑推理服务（需你装）。**

这一批的三个 bug 属于**同一类**：配置字段存在、文档写着、但代码从来没读过它。
它们不崩溃、不报错，只是「你怎么改都没反应」——比报错难查得多。

| 问题 | 性质 | 修法 |
|---|---|---|
| **`base_url` 是个死开关**：`_load()` 把它读进了 `self.config`，但 `chat()` 发的是模块级常量 `CHAT_URL`（硬编码 `https://api.deepseek.com/chat/completions`）。于是配置里改地址毫无效果 —— 想连本机 Ollama 根本不可能，请求照样发去云端然后拿回 402 | **真缺陷（静默失效）** | 新增 `_chat_url()` 从 `config.base_url` 现算端点，兼容 `.../v1`、`.../v1/`、`.../v1/chat/completions` 三种写法；`chat()` 改用它 |
| **`config_dir` 是个死参数**：`__init__` 收下它只拿来 `mkdir`，读写一律走模块级 `DEEPSEEK_CONFIG`。后果是测试无法隔离，只能去碰真实 `config/deepseek.yaml` | 真缺陷 | 新增 `config_path` 属性（跟随 `self.config_dir`），`_load()` / `save()` 统一改用它 |
| **本地模式被「必须有 Key」的门槛挡死**：`is_ready` 只看 `api_key`，而 Ollama / vLLM / LM Studio 通常不校验 `Authorization` | 设计缺陷 | 新增 `provider` 字段（`auto`/`deepseek`/`local`）：`local` 模式下 `is_ready` 只看 `base_url`，且自动补占位 key `"local"`（真 key 存在时不覆盖） |
| **回环请求被代理劫持**：本机 `HTTP_PROXY=http://127.0.0.1:57236` 且无 `NO_PROXY` → 连 `localhost:11434` 也被发去代理，回 **502 Bad Gateway** | 环境坑（极难自诊） | `_bypass_proxy_kwargs()`：回环地址自动 `proxies={"http": None, "https": None}`；云端地址照旧走代理 |
| **`except Exception` 把编程错误伪装成网络故障**：正是它把上一轮引入的 `NameError: CHAT_URL is not defined` 包装成「DeepSeek 调用失败」，差点让 bug 溜过去 | 测试可信度 | 兜底收窄为 `requests.exceptions.RequestException`，并拆出 `ConnectionError` / `Timeout` / `HTTPError` 各自给可操作提示（402 提示改本地模式；连不上提示 `ollama serve`） |
| **没有入口能切换到本地**：`llm.py` 改好了，但配置里没有 `provider` 字段、看板也没有对应控件 —— 用户依然无处可切 | 可用性 | ① `config/deepseek.yaml` 补 `provider: auto`（默认行为不变）；② 看板设置页加「☁️ 云端 / 🖥️ 本地」切换 + 地址输入 + **「🔍 探测」**（调 `list_models()` 拉取本机模型名做下拉，失败静默返回空，不弹红） |

配套新增 `configure()`（一次性改多个连接字段，**只改显式传入的**，
免得切 provider 顺手冲掉 base_url）与 `describe()`（一行状态，给看板/日志用）。

**测试规模：508 → 527 passed / 0 failed**（新增 `tests/test_models_llm.py`，
19 条 → 23 条）。

**负向对照已做**：把两个死配置 bug 临时退回旧实现，
`test_chat_actually_posts_to_the_configured_base_url`、
`test_config_dir_decides_which_file_is_read` 等 3 条立即变红
